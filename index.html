Feed the GPUs.
Not the CPU.

GPUFlow is an ultra-high-bandwidth parallel storage software stack built around an accelerator-initiated, zero-copy data path, so that data moves from NVMe to GPU memory without passing through host CPUs or system memory, and expensive accelerators stop waiting on I/O.

The problem

AI has become data-bound. The I/O path hasn't caught up.

Multimodal models push training sets into the petabytes, and LLM serving now streams KV-cache on every request. GPUs got faster, but the path that feeds them still detours through the CPU.

Today · CPU-centric I/O

NVMe→ Kernel / page cache→ Host DRAM bounce buffer→ TCP/IP→ GPU HBM

Multiple memory copies, context switches, and interrupt overhead. Latency stacks up and GPUs sit idle.

GPUFlow · Accelerator-initiated I/O

NVMe (SPDK)→ RDMA / RoCEv2 · DPU offload→ GPUDirect P2P DMA→ GPU HBM

User-space, kernel-bypass, zero-copy, with a CXL memory tier for hot KV-cache and metadata.

  • The memory wallEvery byte bound for a GPU is copied through host memory at least once, and often more than once.
  • Mixed AI trafficLarge sequential training reads (elephant flows) collide with checkpoints and KV-cache loads (mouse flows), and general-purpose filesystems treat them all the same.
  • Inference latencySlow KV-cache loading raises time-to-first-token and leaves accelerators starved.
  • Operational blind spotsWhen GPU utilization drops, it is hard to tell whether storage, network, or scheduling is to blame.
Technology

Nine core technologies, one GPU-centric data service

GPUFlow combines an end-to-end direct data path, hardware offload, and AI-driven storage intelligence to serve the AI factory's repeated train → infer cycle.

01 · Data path

GPUDirect zero-copy I/O

GPUs pull storage data directly over RDMA, through both POSIX and object (S3) interfaces, with cuFile/cuObject-compatible drivers.

CPU-mediated copies → direct GPU path
02 · Availability

Sub-30-second failover

Distributed mirroring and an automated DR controller keep training running through component or site failures.

Long service outages → RTO ≤ 30 s
03 · Intelligence

AI-powered storage resources

eBPF-based telemetry and access-pattern models predict load and faults, then re-place data and resources ahead of demand.

Static placement → predictive optimization
04 · Cloud native

Unified VM + container storage

One storage stack serves virtual machines and Kubernetes pods on the same nodes, with CSI-driven dynamic provisioning and non-disruptive rebalancing.

Single-runtime storage → heterogeneous runtimes
05 · Offload

DPU-accelerated data processing

NVMe-oF/RDMA, encryption, compression, and checksums are offloaded to a domestic FPGA-based DPU, with UEC-ready congestion control.

CPU-bound protocol stacks → DPU offload
06 · Observability

Workload-aware diagnosis

Correlates GPU idle time with storage and network latency to explain why GPUs starve, from cluster view down to a single volume.

Infrastructure-only monitoring → bottleneck root cause
07 · Validation

Internationally certified performance

Performance is proven through IO500 and MLCommons MLPerf Storage, together with a new benchmark for AI inference storage.

In-house benchmarks → global certification
08 · Memory

CXL metadata acceleration

A CXL memory tier with ghost caching, batched metadata handling, and contention-aware asynchronous I/O scheduling.

Metadata stalls → microsecond-scale access
09 · Inference

KV-cache & framework integration

PyDAOS bindings pass PyTorch/CuPy tensors to storage without conversion, a vLLM connector, and an adaptive GPUDirect/host-staging path selector.

Format conversion → native tensor I/O

Workload-aware placement

  1. Training reads: elephant flows striped over sharded NVMe at full bandwidth
  2. Checkpoints: POSIX/HDF5 with prioritized synchronous replication
  3. KV-cache: object/KV path with a CXL hot tier for low TTFT
  4. Metadata: CXL ghost cache and batched requests

Design principles

  1. No CPU on the data path
  2. POSIX and object, natively
  3. Offload what hardware does better
  4. Measure it, explain it, certify it
